\chapter{Estructura de canales ThingSpeak y codificación de estados}
\label{anexo:estructura_thingspeak_estados}

Este anexo documenta el contrato de datos utilizado por TierraViva en ThingSpeak. Su finalidad es fijar qué publica la estación remota en cada campo del canal, cómo se interpretan los estados operativos y qué correspondencia existe entre la telemetría enviada por Arduino y los nombres internos utilizados por la Raspberry Pi.

\section{Papel de ThingSpeak}

ThingSpeak cumple una función concreta dentro de TierraViva: actuar como \textit{broker} de telemetría entre las estaciones de campo y la Raspberry Pi, recibiendo los datos publicados por las estaciones y permitiendo su consulta posterior desde el sistema de supervisión. Esta decisión simplifica la comunicación entre la estación de campo y el nodo local de supervisión, ya que la estación publica datos en una plataforma intermedia y la Raspberry Pi los consulta posteriormente.

En la versión actual, ThingSpeak se centra en telemetría y estado. La decisión de riego, la gestión de umbrales y la actuación sobre la bomba permanecen en el \textit{firmware} de cada estación.

\section{Formato de publicación}

La estación construye una petición HTTP de actualización del canal utilizando la clave de escritura y los ocho campos definidos. De forma conceptual, la petición tiene la siguiente estructura:

\begin{terminaloutput}
http://api.thingspeak.com/update?
    api_key=<WRITE_API_KEY>
    &field1=<humedad_suelo>
    &field2=<temperatura>
    &field3=<humedad_ambiental>
    &field4=<luminosidad>
    &field5=<presion>
    &field6=<estado_rele>
    &field7=<evento_sistema>
    &field8=<codigo_debug>
\end{terminaloutput}

Las claves reales no deben aparecer en la memoria, en capturas ni en el repositorio. En la documentación se representan mediante marcadores como \texttt{<WRITE\_API\_KEY>}.

\section{Persistencia y trazabilidad}

Las lecturas se almacenan en la tabla \texttt{readings} de SQLite. Las variables principales y los campos de estado \texttt{relay\_state}, \texttt{system\_event} y \texttt{debug\_code} se insertan como valores normalizados cuando están disponibles. Además, la respuesta original de ThingSpeak se conserva en \texttt{raw\_json}, lo que permite mantener trazabilidad completa de la entrada recibida.

Esta doble estrategia resulta útil durante la depuración y la evolución del prototipo: por un lado, las columnas normalizadas facilitan las consultas habituales desde la API y el \textit{dashboard}; por otro, \texttt{raw\_json} permite revisar la respuesta original de ThingSpeak si se detecta una interpretación anómala, un campo ausente o una modificación futura del contrato de datos.

\section{Limitaciones de la versión actual}

ThingSpeak se utiliza para telemetría ascendente y supervisión posterior. El flujo implementado queda definido de la siguiente forma:

\begin{itemize}
    \item la estación publica datos hacia ThingSpeak;
    \item la Raspberry Pi consulta datos desde ThingSpeak;
    \item la decisión de riego se ejecuta localmente en Arduino;
    \item el \textit{dashboard} presenta el estado publicado por las estaciones;
    \item la arquitectura mantiene el control físico de la bomba dentro del \textit{firmware} de estación.
\end{itemize}

Esta decisión es deliberada. La actuación sobre una bomba implica riesgos eléctricos e hidráulicos, por lo que la versión actual prioriza una lógica local con apagado explícito, \textit{cooldown} y comportamiento seguro ante lecturas no válidas.

\section{Conclusión}

La estructura de ThingSpeak de TierraViva define un contrato de datos entre estación, \textit{broker} de telemetría y Raspberry Pi. Los campos \texttt{field1}--\texttt{field5} transportan variables físicas, mientras que \texttt{field6}--\texttt{field8} describen el estado operativo de la estación.

Mantener estable esta correspondencia es esencial para que el \textit{firmware}, el ingestor, la base de datos, la API y el \textit{dashboard} interpreten los datos de forma coherente.
