\chapter{Matriz de trazabilidad entre requisitos y pruebas}
\label{anexo:trazabilidad_requisitos_pruebas}

Este anexo recoge la trazabilidad entre los requisitos definidos para TierraViva y las pruebas empleadas para validar el prototipo. Su finalidad es demostrar que los requisitos funcionales, no funcionales y operativos no quedan únicamente descritos en el diseño, sino relacionados con bloques concretos del sistema y con evidencias de comprobación.

La matriz de trazabilidad conecta tres niveles del proyecto: los requisitos definidos en el Capítulo~\ref{cap:capitulo3}, los bloques técnicos implementados en los Capítulos~\ref{cap:capitulo4}, \ref{cap:implementacion_hardware_firmware} y \ref{cap:implementacion_software_raspberry_nube}, y las pruebas resumidas en el Capítulo~\ref{cap:validacion_pruebas}. El detalle procedimental de cada prueba se recoge en el Anexo~\ref{anexo:plan_pruebas}.

\section{Criterio de trazabilidad}

Para cada requisito se indican los siguientes elementos:

\begin{itemize}
    \item \textbf{Código}: identificador del requisito.
    \item \textbf{Requisito}: descripción resumida del requisito validado.
    \item \textbf{Bloque responsable}: componente o parte del sistema que implementa el requisito.
    \item \textbf{Pruebas asociadas}: casos de prueba definidos en el Anexo~\ref{anexo:plan_pruebas}.
    \item \textbf{Evidencia de validación}: resultado, captura, log, fotografía, registro o comportamiento observado que permite justificar el cumplimiento.
    \item \textbf{Estado}: grado de cobertura alcanzado en el prototipo.
\end{itemize}

El estado \textit{Validado} se utiliza cuando el requisito se ha comprobado mediante pruebas del prototipo. El estado \textit{Cubierto por diseño y documentación} se utiliza para requisitos no funcionales que no dependen de una única prueba, sino de la arquitectura, los manuales, los anexos técnicos y la reproducibilidad del montaje. El estado \textit{Validado con limitación} se reserva para requisitos cumplidos dentro del alcance del TFG, pero que podrían requerir ensayos más prolongados o mediciones adicionales en una versión industrial.

\section{Conclusión}

La matriz de trazabilidad muestra que los requisitos definidos para TierraViva están cubiertos por pruebas concretas, bloques técnicos identificables y evidencias de validación. Esta relación refuerza la defensa técnica del proyecto, porque permite seguir el recorrido completo desde la definición del requisito hasta su comprobación experimental.

Los requisitos funcionales quedan cubiertos mediante pruebas de sensórica, comunicación LTE, ThingSpeak, Raspberry Pi, SQLite, API, \textit{dashboard} y actuación local. Los requisitos no funcionales se justifican mediante la arquitectura modular, la documentación de montaje, la estrategia de pruebas y el comportamiento seguro ante fallos. Las especificaciones temporales y operativas quedan relacionadas con pruebas de ciclos, publicación, \textit{dashboard}, \textit{cooldown}, actuación temporizada y estado seguro.

En conjunto, la trazabilidad confirma que TierraViva no se valida únicamente por descripción, sino mediante una relación explícita entre requisitos, implementación, pruebas y evidencias.
