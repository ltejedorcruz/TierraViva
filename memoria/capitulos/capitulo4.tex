\chapter{Arquitectura final de TierraViva}
\label{cap:capitulo4}

Una vez definidos los requisitos, los materiales y las principales decisiones de diseño, este capítulo presenta la arquitectura final de TierraViva. A diferencia del capítulo anterior, donde se justifican las alternativas valoradas y los criterios de elección, aquí se describe cómo queda organizado el sistema completo y cómo interactúan sus distintos bloques durante el funcionamiento.

La arquitectura final se basa en estaciones de campo autónomas con Arduino UNO, sensores ambientales y de suelo, comunicación LTE mediante el módulo A7670E-LASA, ThingSpeak como plataforma \textit{cloud} y \textit{broker} de telemetría, y un sistema de supervisión implementado sobre Raspberry Pi 5. El sistema cubre el ciclo completo de monitorización y actuación local: adquisición de datos, decisión de riego en la estación, publicación de telemetría, almacenamiento histórico y visualización mediante \textit{dashboard} web.

El cambio principal respecto a planteamientos anteriores es que la Raspberry Pi no actúa como elemento central de decisión del riego. La decisión crítica se desplaza al \textit{firmware} de cada estación, que evalúa sus propias lecturas y aplica reglas locales de seguridad. La Raspberry conserva un papel importante, pero orientado a supervisión, histórico y visualización.

\section{Visión general de la arquitectura}
\label{sec:vision_general_arquitectura}

La arquitectura final de TierraViva se organiza como un sistema IoT distribuido. Las medidas se obtienen en campo, la comunicación se realiza mediante red móvil, la información se publica en una plataforma \textit{cloud} y la supervisión se ejecuta desde una Raspberry Pi 5. La actuación sobre el riego, sin embargo, no depende de una decisión externa enviada desde la Raspberry, sino de reglas locales ejecutadas en cada estación.

El sistema está formado por cuatro elementos principales: las estaciones autónomas de campo A y B, ThingSpeak como \textit{broker} de telemetría, la Raspberry Pi 5 y el \textit{dashboard} web. Las estaciones se encargan de medir, decidir y actuar localmente. ThingSpeak funciona como capa intermedia de telemetría y estado. La Raspberry Pi consulta los datos, mantiene un histórico local y expone una API. El \textit{dashboard} permite supervisar el estado del sistema desde una interfaz web.

La Figura~\ref{fig:arquitectura_final_tierraviva} muestra la arquitectura final del sistema.

\begin{figure}[H]
\centering
\includegraphics[width=\textwidth]{figs/arquitecturaFinalTierraViva.png}
\caption{Arquitectura final de TierraViva con decisión local en las estaciones. Elaboración propia.}
\label{fig:arquitectura_final_tierraviva}

El flujo de funcionamiento comienza en las estaciones de campo. Cada estación mide variables del suelo y del entorno, evalúa localmente si procede regar y, si corresponde, acciona la bomba mediante relé durante un tiempo limitado. Posteriormente publica en ThingSpeak las medidas, el estado del relé, el evento de sistema y el código auxiliar de diagnóstico.

ThingSpeak desacopla las estaciones de la Raspberry Pi: los nodos de campo no necesitan conocer la ubicación del sistema de supervisión ni mantener una conexión directa con él. La Raspberry consulta los canales publicados, almacena un histórico local, expone una API y sirve el \textit{dashboard} web.

La arquitectura final puede resumirse en una separación clara de responsabilidades: las estaciones miden, deciden y actúan; ThingSpeak recibe la telemetría; la Raspberry registra y supervisa; y el \textit{dashboard} presenta la información al usuario. El flujo completo de funcionamiento se representa de forma ampliada en el Anexo~\ref{anexo:diagramas_flujo_funcionamiento}.

\section{Estaciones de campo A y B}
\label{sec:estaciones_campo_ab}

Las estaciones de campo son los nodos autónomos de TierraViva. Su función dentro de la arquitectura final es adquirir datos del entorno, evaluar localmente reglas de riego, accionar la bomba cuando corresponda y publicar telemetría y estado en la plataforma \textit{cloud} . En esta versión del sistema se implementan dos estaciones, denominadas estación A y estación B, con una estructura hardware equivalente y una configuración lógica diferenciada.

Ambas estaciones siguen el mismo diseño base: Arduino UNO como controlador local, sensores de suelo y ambientales, módulo LTE A7670E-LASA para comunicación remota, relé para accionar la bomba de agua y alimentación principal a 12 V con regulación a 5 V mediante LM2596. La diferencia entre ellas no está en la arquitectura física, sino en el identificador de estación y el canal de ThingSpeak utilizado para publicar sus datos.

\section{Solución de comunicaciones}
\label{sec:arquitectura_comunicaciones_lte_http}

La solución de comunicaciones de las estaciones de campo se basa en el módulo LTE A7670E-LASA y en el uso de peticiones HTTP hacia ThingSpeak. Esta solución permite que cada estación publique telemetría y estado desde una ubicación remota sin depender de una red WiFi local ni de una conexión física con la Raspberry Pi.

Desde el punto de vista de capas, el Arduino UNO se comunica localmente con el A7670E-LASA mediante UART y comandos AT. A partir de esos comandos, el módem gestiona el registro en la red móvil LTE, establece el contexto de datos y proporciona conectividad IP. Sobre esta conectividad se utiliza TCP como capa de transporte y HTTP como protocolo de aplicación para enviar la actualización al canal ThingSpeak correspondiente. De de transporte y HTTP como protocolo de aplicación para enviar la actualización al canal ThingSpeak correspondiente. De este modo, aunque el \textit{firmware} trabaje principalmente con comandos AT y peticiones HTTP, la comunicación efectiva hacia la plataforma se apoya en la pila LTE/IP/TCP/HTTP.

\begin{figure}[H]
    \centering
    \includegraphics[width=\textwidth]{figs/figura_4_3_secuencia_lte_http.jpeg}
    \caption{Secuencia funcional de comunicación mediante el módulo A7670E-LASA. Elaboración propia.}
    \label{fig:cap4_secuencia_lte_http}

El flujo implementado en esta primera versión es ascendente: las estaciones publican medidas, estado del relé, evento de sistema y código auxiliar de diagnóstico, y la Raspberry Pi consulta posteriormente esa información desde ThingSpeak. Esta organización resulta adecuada para supervisión, ya que la decisión crítica de riego no depende de la respuesta inmediata de un sistema externo, sino de la evaluación local realizada por la estación.

La solución LTE/IP/TCP/HTTP no proporciona comunicación en tiempo real estricto, pero sí permite completar el flujo necesario para el prototipo: publicación remota de telemetría, consulta desde la Raspberry Pi, almacenamiento histórico y visualización web. El detalle de inicialización del módem, pruebas con comandos AT e integración en \textit{firmware} se desarrolla en el Capítulo~\ref{cap:implementacion_hardware_firmware}.

\section{ThingSpeak como \textit{broker} de telemetría}
\label{sec:thingspeak_capa_intermedia}

ThingSpeak actúa en TierraViva como plataforma IoT y \textit{broker} de telemetría entre las estaciones de campo y la Raspberry Pi. Su función dentro de la arquitectura final es desacoplar la publicación de datos en campo de la supervisión posterior: las estaciones publican telemetría y estado mediante LTE/HTTP, y la Raspberry Pi consulta esa información, mantiene un histórico local y la muestra en el \textit{dashboard}.

La estructura finalmente adoptada se apoya en dos canales diferenciados: \texttt{TierraViva\_A} y \texttt{TierraViva\_B}. Cada canal corresponde a una estación de campo y contiene tanto las variables medidas como la información de estado generada por el \textit{firmware}. En la arquitectura final no se utilizan canales de comandos, ya que la decisión de riego se realiza localmente en cada estación.

\begin{figure}[H]
\centering
\includegraphics[width=0.90\textwidth]{figs/thingspeak_canales_tierraviva.png}
\caption{Canales ThingSpeak creados para las estaciones de TierraViva. Captura propia.}
\label{fig:thingspeak_canales_tierraviva}
\end{figure}

Cada publicación incluye humedad del suelo, variables ambientales, estado del relé, evento de sistema y código auxiliar de diagnóstico. Mantener la misma estructura en ambos canales simplifica el \textit{firmware} y la lógica de supervisión, ya que la Raspberry puede aplicar el mismo proceso de lectura para las estaciones A y B.

En fases anteriores se valoró utilizar ThingSpeak también como mecanismo de control descendente desde la Raspberry Pi hacia las estaciones. Esta posibilidad habría permitido incorporar una capacidad centralizada de configuración o actuación, por ejemplo para modificar parámetros de riego, enviar órdenes supervisadas o ajustar el comportamiento de las estaciones desde una capa superior. Sin embargo, esta opción se descartó para esta primera versión de TierraViva porque obligaba a gestionar órdenes remotas, evitar repeticiones, descartar información obsoleta y garantizar que una entrada antigua no provocase una actuación no deseada, elevando sensiblemente la complejidad del sistema completo más allá del alcance de este trabajo.

En la arquitectura final, ThingSpeak se reserva para telemetría y estado, no para transportar órdenes de riego. La incorporación de un canal descendente de configuración o control se considera una ampliación razonable para futuras versiones, siempre que se acompañe de mecanismos de identificación de comandos, confirmación de ejecución, control de duplicados, caducidad de órdenes y límites de seguridad en la estación.

La estructura completa de campos, nombres internos y códigos publicados se documenta en el Anexo~\ref{anexo:estructura_thingspeak_estados}. La lectura e interpretación de esos datos desde Raspberry Pi se desarrolla en el Capítulo~\ref{cap:implementacion_software_raspberry_nube}.

\section{Raspberry Pi como sistema de supervisión}
\label{sec:raspberry_sistema_supervision}

La Raspberry Pi 5 actúa como sistema de supervisión de TierraViva. Su papel dentro de la arquitectura final no es sustituir a las estaciones de campo, conectarse físicamente a los sensores ni decidir la activación de la bomba, sino consultar la información disponible en ThingSpeak, mantener un histórico local, exponer una API y servir el \textit{dashboard} web.

Esta separación mantiene la coherencia del sistema distribuido. Las estaciones publican su información mediante LTE/HTTP y la Raspberry trabaja sobre los datos ya disponibles en la plataforma \textit{cloud}. A partir de esos datos, construye una vista de supervisión del estado de cada estación.

\begin{figure}[H]
    \centering
    \includegraphics[width=\textwidth]{figs_png/figura_4_5_pipeline_raspberry_supervision.png}
    \caption{Flujo de software de supervisión en Raspberry Pi. Elaboración propia.}
    \label{fig:cap4_pipeline_raspberry_supervision}
\end{figure}

El flujo de software se organiza en cuatro responsabilidades: consulta de ThingSpeak, almacenamiento local en SQLite, exposición de datos mediante FastAPI y visualización en el \textit{dashboard}. La API evita que la interfaz acceda directamente a la base de datos o a ThingSpeak, y permite separar almacenamiento, consulta y presentación.

La Raspberry puede detectar datos antiguos, campos ausentes o pérdida de publicaciones, pero esas incidencias pertenecen a la supervisión. La seguridad de la actuación sigue residiendo en la estación de campo, que es quien controla físicamente el relé y la bomba.

\section{Decisión local de riego y eventos}
\label{sec:decision_local_eventos}

La decisión de riego en TierraViva se ejecuta localmente en cada estación de campo. Esta elección elimina la necesidad de enviar comandos remotos desde la Raspberry Pi y desplaza la responsabilidad crítica al nodo que está físicamente conectado al sistema de riego.

El criterio inicial se basa en una regla verificable de humedad del suelo. La estación solo puede activar el relé si la lectura es válida, se cumple la condición de sequedad, no existe \textit{cooldown} activo y no se detecta ningún error crítico. La actuación se limita siempre por \textit{firmware} para evitar activaciones indefinidas.

\begin{figure}[H]
    \centering
    \includegraphics[width=\textwidth]{figs/figura_4_6_decision_local_riego.jpeg}
    \caption{Lógica conceptual de decisión local de riego en cada estación. Elaboración propia.}
    \label{fig:cap4_decision_local_riego}

Tras cada ciclo, la estación publica en ThingSpeak las medidas ambientales y la información operativa necesaria para supervisar lo ocurrido: estado del relé, evento de sistema y código auxiliar de diagnóstico. De este modo, la Raspberry Pi puede reconstruir el comportamiento de la estación sin participar en la decisión local.

\section{Modo seguro}
\label{sec:modo_seguro}

El modo seguro define el comportamiento que debe adoptar la estación cuando no puede garantizar que una actuación sobre el riego sea correcta. Dado que TierraViva acciona físicamente una bomba de agua, el criterio adoptado es conservador: ante una lectura inválida, reinicio, fallo de comunicación, \textit{cooldown} activo o estado no verificable, la bomba debe permanecer apagada.

\begin{figure}[H]
    \centering
    \includegraphics[width=\textwidth]{figs_png/figura_4_7_modo_seguro_estacion.png}
    \caption{Principio de modo seguro aplicado en las estaciones de TierraViva. Ante reinicio, lectura inválida, fallo de publicación, \textit{cooldown} o finalización del tiempo de riego, el sistema prioriza mantener el relé desactivado y la bomba apagada. Elaboración propia.}
    \label{fig:cap4_modo_seguro_estacion}
\end{figure}

El modo seguro se aplica tanto en el arranque como durante el funcionamiento normal. El \textit{firmware} debe configurar el relé en estado desactivado al iniciar la estación, descartar lecturas incoherentes para la actuación, limitar siempre el tiempo de riego y aplicar un periodo mínimo entre activaciones.

La pérdida de comunicación no debe interpretarse como una orden de riego ni como una condición que deje la bomba activa. En la arquitectura final, la comunicación se utiliza para supervisión y trazabilidad, mientras que la seguridad de la actuación permanece bajo control local de la estación.

El análisis completo de riesgos se desarrolla en el Anexo~\ref{anexo:gestion_riesgos}. Las pruebas asociadas al modo seguro, actuación, sensores y comunicación se recogen en el Anexo~\ref{anexo:plan_pruebas}, y los flujos de fallo se resumen en el Anexo~\ref{anexo:diagramas_flujo_funcionamiento}.
