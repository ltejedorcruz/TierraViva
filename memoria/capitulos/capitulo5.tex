\label{sec:preparacion_arduino_uno}

Aunque la placa recibía alimentación por USB, inicialmente no aparecía ningún puerto disponible en el entorno de desarrollo. La estación combina sensores digitales conectados al bus I2C con un sensor capacitivo de humedad de suelo leído mediante entrada analógica.

El sensor capacitivo de humedad del suelo se validó mediante lecturas brutas en \texttt{A0}. En reposo mostró valores estables alrededor de \texttt{569--570}, mientras que al modificar las condiciones de contacto descendió aproximadamente al rango \texttt{248--356}. Esta prueba no constituye una calibración agronómica definitiva, pero sí confirmó que el sensor respondía ante cambios físicos y que el sentido de variación era utilizable para la lógica de riego.

La humedad del suelo se mantuvo inicialmente como lectura dependiente de calibración, mientras que temperatura, humedad relativa, presión y luminosidad se conservaron como variables de contexto para interpretar el estado de la estación. Con ello quedó validado el bloque de sensórica antes de estructurar el \textit{firmware} de adquisición.

\section{\textit{Firmware} de adquisición}
\label{sec:firmware_adquisicion}

Una vez comprobado el funcionamiento de los sensores, el siguiente paso consistió en organizar el \textit{firmware} de adquisición de la estación. Este \textit{firmware} no se limita a leer variables y enviarlas a la nube, sino que también incorpora la lógica local mínima necesaria para decidir si debe activarse el riego.

El \textit{firmware} se organiza en varios bloques funcionales. En primer lugar, se inicializan los sensores y el módem LTE. Después, en cada ciclo de ejecución, se leen las variables ambientales y de suelo. A partir de esas lecturas, se actualiza el estado interno de seguridad de la estación y se decide si procede activar el riego. Por último, la estación publica una actualización en ThingSpeak con las medidas y el estado operativo.

La Figura~\ref{fig:ciclo_firmware_estacion} sintetiza el ciclo lógico ejecutado por el \textit{firmware} de estación. La estación no depende de una orden externa para cerrar el ciclo de control: mide, valida, decide, actúa si procede y publica el estado resultante.

\begin{figure}[H]
    \centering
    \makebox[\textwidth][c]{%
        \includegraphics[width=0.8\textwidth]{figs_png/ciclo_firmware_estacion.png}%
    }
    \caption{Ciclo lógico del \textit{firmware} de estación.}
    \label{fig:ciclo_firmware_estacion}
\end{figure}

En la función \texttt{setup()} se configuran el puerto serie de depuración, el bus I2C, los sensores, el pin de relé y el módem LTE. El relé se inicializa en estado desactivado para que un reinicio del Arduino no pueda provocar una activación accidental de la bomba. Durante el ciclo principal, el \textit{firmware} lee las variables de suelo y ambiente, convierte la humedad del suelo a escala porcentual, valida las medidas y actualiza el estado interno de seguridad.

La lógica de decisión se apoya en variables como \texttt{safeMode}, \texttt{sensorOk}, \texttt{validCycleCount} y \texttt{dryCycleCount}. Además, diferencia entre el evento principal del sistema, almacenado en \texttt{systemEventCode}, y el código auxiliar de diagnóstico, almacenado en \texttt{debugCode}. Esta separación permite publicar en ThingSpeak no solo el estado de riego, sino también el motivo de la decisión.

El código completo se mantiene en el repositorio del proyecto.

La decisión local se apoya en tres mecanismos: umbral de humedad, confirmación por ciclos consecutivos y tiempo mínimo entre riegos. No se activa el riego por una única lectura aislada, ya que una medida puntual puede verse afectada por ruido, contacto irregular del sensor o pequeñas variaciones del montaje. Además, el periodo de \textit{cooldown} evita activaciones repetidas en poco tiempo.

La función de decisión local se muestra en el Código~\ref{cod:decision_local_riego}. Si existe un error de sensores o un periodo de \textit{cooldown} activo, la estación no permite el riego y actualiza los códigos de estado correspondientes. Si no existe bloqueo, compara la humedad del suelo con el umbral normal o seguro según el estado interno de la estación.

\begin{code}[H]
\begin{lstlisting}[language=C++]
bool shouldIrrigate() {
  if (!sensorOk) {
    systemEventCode = 400;
    debugCode = 400;
    return false;
  }

  if (cooldownActive()) {
    systemEventCode = 429;
    debugCode = 429;
    return false;
  }

  if (safeMode) {
    return (soilPercent <= SAFE_SOIL_THRESHOLD) &&
           (dryCycleCount >= SAFE_CONFIRM_DRY_CYCLES);
  }

  return (soilPercent <= NORMAL_SOIL_THRESHOLD) &&
         (dryCycleCount >= NORMAL_CONFIRM_DRY_CYCLES);
}
\end{lstlisting}
\caption[Decisión local de riego en la estación]{Decisión local de riego en la estación}
\label{cod:decision_local_riego}
\end{code}

Cuando la estación decide regar, la actuación se realiza mediante una función temporizada de \textit{firmware}. Durante el riego, el evento principal se marca como \texttt{210}; al finalizar el intervalo configurado, el relé se apaga explícitamente y el evento pasa a \texttt{211}. De este modo, la parada de la bomba no depende de una orden externa ni de la Raspberry Pi.

Tras la lectura de sensores, la actualización del modo seguro y la posible actuación sobre el relé, el \textit{firmware} prepara el estado de la estación para su publicación. Esta publicación no se desarrolla en detalle en esta sección para evitar duplicidades, ya que la correspondencia completa entre variables y campos de ThingSpeak se documenta en la Sección~\ref{sec:envio_datos_thingspeak}.

De este modo, la estación conserva un ciclo completo de funcionamiento autónomo: mide, interpreta, decide, actúa cuando procede y deja preparado el estado operativo para su envío. La Raspberry Pi puede consultar posteriormente esos datos y representarlos en el \textit{dashboard}, pero no interviene en el cierre del bucle de control.

Las dependencias principales del \textit{firmware}, incluyendo las librerías utilizadas para comunicación serie, bus I2C, lectura de sensores y manejo de cadenas, se resumen en el Anexo~\ref{anexo:manual_instalacion_sistema}.

Una vez validado el módulo por separado, se abordó la conexión con Arduino UNO. La comunicación se realiza mediante interfaz UART y comandos AT. Como el puerto serie \textit{hardware} del Arduino se utiliza también para programación y depuración por USB, se empleó \texttt{SoftwareSerial} para crear un puerto serie adicional destinado al módem. En el montaje de la estación se mantuvieron los pines \texttt{D10} y \texttt{D11}, ya cableados y probados durante las fases anteriores.

El pin \texttt{D10} del Arduino se utiliza como recepción del puerto serie software y se conecta al pin \texttt{TXD} del A7670E-LASA. El pin \texttt{D11} se utiliza como transmisión hacia el módem y se conecta al pin \texttt{RXD} del A7670E-LASA mediante un divisor resistivo. Esta adaptación es necesaria porque Arduino UNO trabaja con niveles lógicos de 5 V, mientras que la entrada serie del módulo no debe recibir directamente ese nivel si no existe adaptación integrada.

El divisor resistivo se dimensiona mediante la Ecuación~\ref{ec:divisor_resistivo_rxd}.

\begin{myequation}[h]
\begin{equation}
V_{\mathrm{RXD}} =
V_{\mathrm{TX,Arduino}}
\cdot
\frac{R_2}{R_1 + R_2}
\label{ec:divisor_resistivo_rxd}
\end{equation}
\caption[Cálculo de la tensión de salida del divisor resistivo]{Cálculo de la tensión aplicada a la entrada RXD del A7670E-LASA mediante un divisor resistivo}
\end{myequation}

En esta expresión, \(V_{\mathrm{TX,Arduino}}\) representa la tensión de salida del pin de transmisión del Arduino, \(R_1\) la resistencia situada entre el pin \texttt{D11} y el nodo conectado a \texttt{RXD}, y \(R_2\) la resistencia situada entre dicho nodo y masa. El objetivo de este divisor no es modificar la información transmitida por la UART, sino adaptar el nivel eléctrico de la señal para que la entrada \texttt{RXD} del módem no reciba directamente el nivel lógico de 5 V procedente del Arduino UNO.

La señal en sentido contrario, desde \texttt{TXD} del A7670E-LASA hacia \texttt{D10} del Arduino, no requiere el mismo divisor porque no procede de una salida lógica de 5 V del Arduino. Por tanto, la adaptación se aplica únicamente en el sentido Arduino~\(\rightarrow\)~módem.

La alimentación del módulo se trató como un aspecto crítico. Los módulos de comunicación celular pueden presentar consumos variables, especialmente durante el registro en red y la transmisión de datos, por lo que la alimentación y el cableado deben respetar las recomendaciones de diseño del fabricante y de la placa de evaluación utilizada \cite{simcom_a7670_hardware_design,waveshare_a7670e_hat}. En la estación, la alimentación parte de una fuente principal de 12 V y se regula mediante el LM2596 ajustado a 5 V para los elementos compatibles.

En el \textit{firmware}, la comunicación con el módem se estabilizó a \texttt{9600} baudios, ya que \texttt{SoftwareSerial} en Arduino UNO puede volverse inestable a velocidades superiores. La configuración final combinó pines \texttt{D10}/\texttt{D11}, divisor resistivo hacia \texttt{RXD}, secuencia AT, activación de datos móviles y envío HTTP.

La gestión de errores se resolvió de forma conservadora: si el módem no responde, si el registro LTE no se completa, si falla el contexto de datos o si la respuesta HTTP no es válida, la estación marca la conectividad como no preparada y reintenta posteriormente sin bloquear el ciclo principal. Además, se tuvo en cuenta la memoria SRAM limitada del Arduino UNO, evitando URLs impresas completas, cadenas excesivas y búferes sobredimensionados.

El resultado de esta fase fue la integración estable del A7670E-LASA dentro de la estación de campo. El módulo quedó conectado al Arduino mediante UART software, con adaptación de nivel en la línea hacia \texttt{RXD}, alimentación estabilizada y una secuencia de comandos capaz de registrar el módem en red, activar datos móviles y realizar peticiones HTTP. El conexionado eléctrico, la adaptación de nivel y la alimentación estabilizada del módem se documentan en el Anexo~\ref{anexo:esquemas_electricos}.

\section{Envío de datos a ThingSpeak}
\label{sec:envio_datos_thingspeak}

Una vez integrados los sensores y validado el módulo LTE, la estación publica su telemetría en ThingSpeak mediante una petición HTTP de actualización de canal \cite{thingspeak_write_data}. El \textit{firmware} construye la petición con la clave de escritura y los campos correspondientes a las variables medidas y al estado operativo de la estación.

La correspondencia completa entre \texttt{field1}--\texttt{field8}, variables internas y códigos de estado se documenta en el Anexo~\ref{anexo:estructura_thingspeak_estados}. En este capítulo interesa destacar el criterio de implementación: la publicación se considera correcta únicamente cuando el módem informa de una respuesta HTTP con código 200.

\label{fig:confirmacion_http_thingspeak}
\end{figure}

Aunque en el lenguaje informal pueda interpretarse como una confirmación o acuse de recibo de la publicación, no se trata de un ACK de nivel TCP, sino de una comprobación a nivel de aplicación basada en el código de respuesta HTTP devuelto por ThingSpeak.

Los reintentos se plantean de forma controlada: si una publicación falla, la estación vuelve a intentarlo en el siguiente ciclo de telemetría, evitando bucles indefinidos que puedan bloquear el \textit{firmware} o aumentar el consumo. Además, un fallo de publicación no afecta directamente a la seguridad del riego, ya que la decisión de actuación permanece en la estación. La consecuencia principal de una pérdida temporal de conectividad es la ausencia de una muestra en la nube, no la pérdida del control local de la bomba.

\section{Actuación y alimentación de la estación}
\label{sec:control_rele_led_bomba}
\label{sec:alimentacion_estacion}

La actuación física sobre el riego se realiza mediante un módulo relé controlado desde el Arduino UNO. El Arduino no alimenta la bomba directamente: únicamente gobierna la señal de control del relé, mientras que la bomba de agua recibe alimentación desde la línea de 12 V. Esta separación evita que la corriente de potencia circule por el microcontrolador y permite mantener un estado seguro por defecto.

La Figura~\ref{fig:alimentacion_actuacion_estacion} resume la distribución eléctrica utilizada en la estación. La línea principal de 12 V alimenta la carga de actuación y sirve como entrada al regulador LM2596, ajustado a 5 V para alimentar la electrónica de control. Todos los bloques comparten masa común para que las señales digitales, la comunicación serie y las lecturas de sensores tengan una referencia eléctrica válida.

    \centering
    \makebox[\textwidth][c]{%
        \includegraphics[width=0.8\textwidth]{figs_png/alimentacion_actuacion_estacion.png}%
    }
\caption{Distribución de alimentación y actuación en una estación TierraViva.}
\label{fig:alimentacion_actuacion_estacion}
\end{figure}

El pin digital \texttt{D7} se utiliza para controlar el relé. Este se inicializa apagado desde el arranque, de forma que un reinicio de la placa no pueda activar accidentalmente la bomba. La conexión de potencia utiliza los contactos \texttt{COM} y \texttt{NO}; al emplear el contacto normalmente abierto, la bomba permanece apagada mientras no exista una activación expresa desde el \textit{firmware}.

Antes de conectar los módulos electrónicos, el LM2596 debe ajustarse y verificarse con multímetro. Esta comprobación evita aplicar una tensión incorrecta al Arduino, sensores o módem. El módulo A7670E-LASA requiere especial atención porque los módulos de comunicación celular pueden presentar picos de consumo durante el registro en red y la transmisión de datos; por ello se incorporan condensadores de estabilización próximos a su entrada de alimentación.

Desde el punto de vista funcional, la bomba se activa únicamente durante el intervalo configurado por \textit{firmware}. Ante una lectura inválida, una condición interna incoherente o un periodo de \textit{cooldown} activo, la estación mantiene la bomba apagada y publica los códigos de estado correspondientes cuando la comunicación está disponible.

Si la bomba utilizada es de corriente continua, resulta recomendable incorporar protección frente a transitorios, especialmente al tratarse de una carga inductiva. Esta protección puede realizarse mediante un diodo de rueda libre o \textit{flyback} colocado en paralelo con la bomba, con la polaridad adecuada, o mediante un módulo de actuación que ya incorpore protección equivalente.

Aunque el sistema se valida inicialmente con una batería de 12 V, la arquitectura deja preparada una evolución hacia alimentación autónoma mediante panel solar. Esta ampliación no se considera validada en el prototipo actual, ya que requeriría dimensionar batería, panel y regulador de carga a partir del consumo real de Arduino, sensores, módem LTE, relé, bomba, frecuencia de telemetría y tiempos de actuación.
