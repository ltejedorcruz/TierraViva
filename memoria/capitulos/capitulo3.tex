\chapter{Métodos, materiales y decisiones de diseño}
\label{cap:capitulo3}
Este capítulo concreta el diseño de TierraViva a partir del marco técnico descrito en el capítulo anterior. Aquí se fijan los requisitos del sistema, se explican los criterios de elección y se documentan las decisiones que han guiado el prototipo: qué debe medir cada estación, cómo se comunica, qué papel conserva la Raspberry Pi y qué condiciones deben cumplirse antes de actuar sobre el riego.

A diferencia del estado del arte, el análisis se centra ya en el proyecto desarrollado. Algunas decisiones se tomaron de forma incremental, a medida que se validaban sensores, comunicaciones y software de supervisión. Por ello, el capítulo no se limita a enumerar materiales, sino que justifica por qué TierraViva adopta una arquitectura distribuida con decisión local en las estaciones.

\section{Requisitos funcionales del sistema}
\label{sec:requisitos_funcionales}

Los requisitos funcionales definen las capacidades que debe proporcionar el sistema para cumplir con el alcance planteado para el proyecto. En el caso de TierraViva, estos requisitos no se limitan a la lectura de sensores, sino que cubren el ciclo completo de funcionamiento: adquisición de datos en campo, transmisión remota, almacenamiento, visualización, toma de decisiones y actuación sobre el riego.

La definición de estos requisitos permite separar con claridad qué debe hacer el sistema de cómo se implementa cada parte. Esta distinción es importante porque las decisiones tecnológicas concretas se justifican en apartados posteriores. En este punto se describe el comportamiento esperado del prototipo y la forma prevista de comprobar que cada función queda cubierta durante la validación.

El sistema se plantea a partir de estaciones de campo capaces de obtener medidas del entorno, evaluar localmente reglas sencillas de riego y enviar la información a una plataforma intermedia. A partir de esos datos, el sistema de supervisión debe poder registrar el histórico, visualizar el estado del prototipo y mostrar las actuaciones realizadas por cada estación. La estación de campo debe ejecutar la actuación de forma autónoma y segura, evitando activaciones indefinidas, riegos repetidos o estados peligrosos ante lecturas inválidas, errores de comunicación o fallos eléctricos.

Los tres primeros requisitos se relacionan con la adquisición de información en campo. La humedad del suelo es la variable más directamente vinculada con la decisión de riego, mientras que las variables ambientales permiten interpretar mejor las condiciones en las que se encuentra la zona monitorizada. En esta fase no se busca realizar un análisis agronómico completo, sino obtener un conjunto de medidas suficiente para validar el comportamiento del prototipo.

Los requisitos RF-04, RF-05 y RF-06 cubren el flujo de datos desde la estación hasta la plataforma intermedia y el sistema de supervisión. La telemetría debe recibirse de forma remota, quedar asociada a una estación concreta y almacenarse para su consulta posterior. Esta trazabilidad es necesaria para que el sistema no dependa únicamente de la última lectura recibida y para poder analizar la evolución de las variables durante las pruebas.

El requisito RF-07 se centra en la interacción con el usuario. Aunque el sistema pueda funcionar internamente, su utilidad queda limitada si no existe una forma clara de consultar el estado de las estaciones. Por ello, el dashboard debe permitir revisar las medidas recientes, detectar si los datos llegan correctamente y comprobar el estado general del sistema sin recurrir a mensajes de consola o consultas manuales a la base de datos.

Los requisitos RF-08, RF-09 y RF-10 introducen la parte de control. En la arquitectura final, la decisión de riego se ejecuta localmente en cada estación mediante reglas verificables, especialmente durante esta primera versión del prototipo. La estación no depende de una decisión externa para actuar: evalúa sus sensores, comprueba las condiciones de seguridad, activa la bomba si corresponde y publica después su estado. Esta publicación incluye las medidas ambientales, el estado del relé, el evento de sistema y el código auxiliar de diagnóstico. Con esa información, la Raspberry Pi puede supervisar lo ocurrido y conservar un histórico sin convertirse en un punto único de decisión para el riego.

El requisito RF-11 se ha definido de forma explícita porque la actuación sobre riego implica un riesgo mayor que la simple monitorización. Un fallo de software, una lectura inválida, un reinicio inesperado o una comunicación incompleta no deben provocar una activación indefinida de la bomba. Por ese motivo, el sistema debe adoptar un comportamiento conservador: ante una situación no válida o no verificable, el estado seguro será mantener la bomba apagada.

Estos requisitos funcionales servirán como base para las decisiones de diseño del resto del capítulo y para la estrategia de validación descrita más adelante. Cada requisito debe poder relacionarse con una prueba concreta, de forma que el cumplimiento del sistema no se justifique solo por diseño, sino también mediante evidencias experimentales.

El sistema debe mantener un equilibrio entre ambición técnica y viabilidad. No se pretende desarrollar un producto industrial cerrado, pero sí una solución suficientemente robusta, ordenada y reproducible como para demostrar el funcionamiento completo de la arquitectura propuesta. La modularidad es uno de los requisitos más importantes del proyecto. Separar el sistema en bloques permite desarrollar y validar cada parte de forma progresiva, evitando que la actuación sobre el riego dependa de un único componente externo. Por ejemplo, la lectura de sensores puede comprobarse antes de integrar la comunicación remota, y la visualización puede probarse inicialmente con datos simulados o recibidos por otros medios. Esta forma de trabajo reduce el riesgo de que un fallo en una capa impida avanzar en el resto del sistema.

El bajo coste no se interpreta como elegir siempre el componente más barato, sino como seleccionar materiales razonables para el alcance del prototipo. En un TFG resulta más adecuado emplear plataformas y módulos accesibles, bien documentados y fáciles de sustituir, siempre que proporcionen prestaciones suficientes para validar la arquitectura. Esta decisión también favorece la reproducibilidad, ya que otros estudiantes o desarrolladores podrían replicar el montaje sin depender de equipos propietarios o excesivamente específicos.

La reproducibilidad está directamente relacionada con la documentación del proceso. Las conexiones, configuraciones, pruebas, errores encontrados y decisiones de diseño deben quedar registrados con suficiente detalle. Esto no solo facilita la redacción de la memoria, sino que también permite justificar ante el tribunal que el sistema no se ha construido como una prueba puntual difícil de repetir, sino como un prototipo técnico verificable.

La facilidad de depuración también ha condicionado el planteamiento del trabajo. En un sistema con sensores, comunicaciones, base de datos, dashboard y actuación física, no es práctico probar todo únicamente al final. El sistema debe permitir observar salidas intermedias, comprobar lecturas por separado, revisar registros, analizar respuestas de comunicación y validar la actuación en condiciones controladas. Esta capacidad resulta clave para detectar errores de cableado, problemas de alimentación, fallos de formato en los datos o comportamientos inesperados en la lógica de control.

El consumo energético debe mantenerse en valores razonables. Aunque la optimización completa de autonomía no forma parte del núcleo del TFG, el sistema se orienta a estaciones de campo que podrían funcionar con batería o alimentación solar en futuras versiones. Por ello, el diseño no debe ignorar el consumo de módulos de comunicación, sensores y actuadores. En especial, la actuación sobre una bomba de agua y el uso de comunicaciones remotas obligan a considerar la alimentación como una restricción real del sistema.

La tolerancia a fallos es especialmente relevante porque TierraViva incorpora actuación sobre el riego. Un error en una medida puede ser aceptable si queda registrado y no se utiliza de forma crítica, pero un error que provoque la activación indefinida de la bomba sí comprometería el funcionamiento del sistema. Por este motivo, el comportamiento ante fallos debe ser conservador: si falta información, si una lectura no es válida o si se supera un límite de seguridad, el sistema debe priorizar el apagado de la bomba.

La escalabilidad se plantea de forma limitada pero necesaria. El prototipo debe poder trabajar con más de una estación de campo, al menos desde el punto de vista de identificación, almacenamiento y visualización. Esto implica que los datos no deben tratarse como si procedieran de un único nodo, sino que deben conservar la referencia de la estación de origen. Esta decisión facilita futuras ampliaciones a varias zonas de riego o parcelas diferenciadas.

Por último, la claridad de visualización y la adecuación al alcance académico condicionan la forma de presentar el sistema. El dashboard debe servir para entender el estado del prototipo sin obligar al usuario a interpretar directamente tramas, códigos internos o registros de depuración. Al mismo tiempo, el proyecto debe evitar prometer funcionalidades que no puedan validarse con rigor dentro del tiempo disponible. En este sentido, se priorizan decisiones simples, trazables y defendibles frente a soluciones más complejas que aumentarían el riesgo de integración sin aportar una mejora proporcional al objetivo del TFG.

Las especificaciones temporales no se plantean como valores rígidos e inmodificables, sino como parámetros iniciales de diseño. Durante el desarrollo y la validación del prototipo pueden ajustarse en función de los resultados obtenidos, siempre manteniendo dos criterios principales: evitar comunicaciones innecesarias y garantizar que cualquier actuación sobre el riego quede limitada en el tiempo.

Los parámetros temporales se han definido como valores configurables del firmware. Durante las pruebas pueden emplearse intervalos reducidos para acelerar la validación del sistema, mientras que en un funcionamiento más estable conviene utilizar periodos más conservadores. Lo importante desde el punto de vista de diseño no es fijar un único valor definitivo, sino garantizar que la estación trabaja con ciclos controlados y que cualquier actuación sobre la bomba queda limitada temporalmente.

La actualización del dashboard puede realizarse con mayor frecuencia que la publicación de datos de las estaciones. Esto permite que la interfaz muestre de forma dinámica la última lectura recibida, la antigüedad del dato o posibles avisos de desconexión, sin asumir que cada refresco implica una nueva medida en campo.

La actuación sobre la bomba es el punto más crítico de estas especificaciones. Por ello, el firmware debe limitar siempre el tiempo de activación, aplicar un periodo mínimo entre riegos y mantener la bomba apagada ante lecturas inválidas, reinicios, pérdida de comunicación o estados no verificables. Esta lógica refuerza el criterio general del sistema: TierraViva puede actuar sobre el riego, pero solo cuando la información disponible y el estado operativo son suficientemente fiables.

\section{Metodología de trabajo}
\label{sec:metodologia_trabajo}

La metodología seguida en TierraViva se ha basado en un desarrollo incremental por bloques. En lugar de intentar construir el sistema completo desde el primer momento, se ha dividido el proyecto en fases más pequeñas, cada una orientada a validar una parte concreta de la arquitectura. Este enfoque resulta adecuado para un sistema IoT con sensores, comunicaciones, almacenamiento, visualización y actuación física, ya que permite aislar errores y reducir el riesgo de integración.

La idea principal ha sido avanzar desde pruebas controladas hacia una arquitectura cada vez más cercana al funcionamiento final. Primero se analizaron las necesidades del problema y las alternativas tecnológicas disponibles. Después se desarrollaron prototipos parciales para comprobar sensores, comunicaciones, almacenamiento y visualización. Finalmente, las distintas partes se fueron conectando hasta formar una solución de monitorización y control más completa.

Esta forma de trabajo también ha permitido documentar decisiones y cambios de enfoque. En un proyecto de este tipo, no todas las decisiones se pueden cerrar desde el principio, ya que algunas dependen de la disponibilidad real de hardware, de la facilidad de integración o de los resultados obtenidos en pruebas. Por ello, la metodología no se ha limitado a implementar una arquitectura previamente fija, sino que ha incorporado revisión, validación y corrección de decisiones durante el desarrollo.

Las primeras fases permitieron transformar la necesidad inicial en requisitos técnicos y revisar las alternativas de sensorización, comunicaciones, plataformas embebidas, almacenamiento y visualización. A partir de esa revisión se definió una arquitectura por bloques, con estaciones autónomas de campo, plataforma intermedia, sistema de supervisión y actuación local.

El prototipo local previo con Raspberry Pi permitió validar una primera cadena de adquisición, almacenamiento, API y dashboard antes de adoptar la arquitectura final con LTE y ThingSpeak. Posteriormente se validaron sensores, comunicaciones y actuación por separado, evitando mezclar problemas de cableado, alimentación, módem, backend o lógica de riego en una única fase de integración.

La integración final conectó adquisición, publicación de telemetría, almacenamiento local, visualización, decisión local y actuación sobre el relé. Durante este proceso se documentaron incidencias, alternativas descartadas y cambios de enfoque, especialmente la separación entre supervisión y control local. Esta decisión trasladó la lógica crítica de riego al firmware de cada estación y dejó la Raspberry Pi como sistema de consulta, histórico y visualización.

\section{Arquitectura general planteada}
\label{sec:arquitectura_general_planteada}

A partir de los requisitos definidos en los apartados anteriores, la arquitectura general de TierraViva se plantea como un sistema IoT distribuido, formado por estaciones autónomas de campo, una plataforma intermedia de comunicación y un sistema de supervisión basado en Raspberry Pi. El objetivo de esta arquitectura es separar claramente la adquisición de datos, la decisión local, la actuación física, la publicación de telemetría, el almacenamiento histórico y la visualización.

La arquitectura se ha diseñado teniendo en cuenta una restricción importante: las estaciones de campo no están conectadas físicamente a la Raspberry Pi. Por tanto, no se puede asumir una comunicación directa mediante USB, puerto serie o red local entre ambos extremos. Las estaciones deben poder enviar datos de forma remota mediante el módulo LTE, y la Raspberry debe consultar esa información desde la plataforma intermedia. Esto condiciona el diseño completo del sistema y evita que el riego dependa de una conexión local o de una orden enviada desde la Raspberry.

En términos generales, el sistema se divide en cuatro bloques principales:

\begin{itemize}
    \item \textbf{Estaciones autónomas de campo}: encargadas de medir las variables del entorno, evaluar reglas locales de riego, accionar la bomba mediante relé y publicar telemetría y estado.
    \item \textbf{Capa de comunicaciones y plataforma intermedia}: responsable de recibir los datos publicados por las estaciones y hacerlos accesibles para consulta remota.
    \item \textbf{Sistema de supervisión}: implementado sobre Raspberry Pi, encargado de consultar datos, almacenarlos, exponer una API y servir el dashboard.
    \item \textbf{Interfaz de usuario}: orientada a visualizar el estado del sistema, revisar el histórico y supervisar las actuaciones realizadas por las estaciones.
\end{itemize}

La Figura~\ref{fig:arquitectura_general_tierraviva} muestra una visión general de la arquitectura planteada.

  \hspace{-0.5cm}\centerline{\resizebox{1.2\textwidth}{!}{\includegraphics{figs/arquitecturaTierraViva.png}}}
  \caption{Arquitectura general planteada para TierraViva.}
\label{fig:arquitectura_general_tierraviva}
\end{figure}

En esta sección no se entra todavía en el detalle de implementación; ese desarrollo se reserva para el capítulo siguiente. Lo importante aquí es dejar fijado el reparto de responsabilidades entre estaciones, plataforma intermedia, Raspberry Pi y dashboard. Las estaciones de campo se encargan de la interacción directa con el entorno físico y de la actuación sobre el riego. ThingSpeak permite publicar y consultar la telemetría de forma remota. La Raspberry Pi actúa como sistema de supervisión, histórico y visualización, sin convertirse en el elemento responsable de decidir la activación de la bomba.

Esta división condiciona el resto de decisiones del proyecto. La actuación sobre el riego debe ejecutarse localmente en la estación, donde se encuentra físicamente la bomba. De este modo, una pérdida de conectividad o una indisponibilidad temporal de la Raspberry no impide que la estación conserve un comportamiento seguro. El detalle de la arquitectura final, incluyendo los canales concretos de ThingSpeak, el flujo de telemetría, la publicación de estado y el papel de la Raspberry Pi como sistema de supervisión, se desarrolla en el Capítulo~\ref{cap:capitulo4}.

\section{Elección de variables y sensores}
\label{sec:eleccion_variables_sensores}

La selección de variables medidas se ha realizado teniendo en cuenta el papel que deben cumplir dentro del prototipo: monitorizar el estado de una zona de cultivo y aportar información suficiente para alimentar la decisión local de riego en cada estación. No se pretende medir todos los parámetros agronómicos posibles, sino elegir un conjunto reducido de variables que permita validar el comportamiento del prototipo de forma razonable, reproducible y coherente con el alcance del TFG.

En TierraViva se combinan variables del suelo y variables ambientales. La humedad del suelo se considera la variable principal para la decisión local de riego, ya que aporta información directa sobre la disponibilidad de agua en el sustrato. Las variables ambientales, como temperatura, humedad relativa, presión atmosférica y luminosidad, no sustituyen a la humedad del suelo, pero ayudan a interpretar el contexto en el que evoluciona la zona monitorizada. Esta combinación es habitual en sistemas de agricultura de precisión basados en sensores, donde el interés no está solo en una lectura aislada, sino en la observación conjunta del entorno \cite{soussi2024smart}.

La humedad del suelo se ha seleccionado como variable principal porque es la más relacionada con la necesidad de riego. Un sistema que decidiera únicamente a partir de temperatura o luminosidad podría detectar condiciones de calor o exposición solar, pero no sabría si el terreno conserva todavía suficiente agua. Por este motivo, la lógica de riego debe apoyarse prioritariamente en el estado del sustrato.

Para esta medida se ha utilizado un sensor capacitivo de humedad de suelo. Frente a sensores resistivos más simples, este tipo de sensor reduce el problema de corrosión asociado al contacto con humedad, ya que la medida se basa en el cambio capacitivo del entorno del sensor. Además, proporciona una salida analógica fácil de leer desde Arduino mediante una entrada ADC. En el prototipo se emplea un módulo capacitivo de humedad de suelo V1.2 compatible con Arduino, comercializado por AZ-Delivery, cuya documentación lo describe como un sensor analógico de medida capacitiva orientado a la monitorización de humedad en sustrato \cite{azdelivery_soil_v12}. La lectura se obtiene inicialmente como un valor bruto, por lo que no debe interpretarse directamente como un porcentaje absoluto sin calibración previa.

Esto afecta directamente a la forma de validar la lectura. El sistema puede trabajar inicialmente con valores \textit{raw}, pero para una decisión de riego más ajustada será necesario calibrar el sensor con muestras de suelo seco y suelo húmedo. Durante las primeras pruebas se comprobó que el valor analógico variaba al modificar las condiciones de contacto del sensor, lo que permitió validar la respuesta básica de la lectura antes de plantear una calibración completa en sustrato real.

La temperatura ambiente se incluye como variable de contexto. No permite decidir por sí sola si hay que regar, pero ayuda a interpretar el comportamiento del suelo. A igualdad de humedad inicial, un entorno con temperatura elevada puede favorecer mayor evaporación y acelerar la pérdida de agua. Registrar la temperatura permite entender mejor la evolución de las medidas y comparar condiciones de prueba distintas.

La humedad relativa aporta información complementaria sobre el ambiente. Una humedad relativa baja puede estar asociada a mayor demanda evaporativa, mientras que una humedad relativa elevada puede indicar condiciones en las que la pérdida de agua por evaporación es menor. En esta primera versión del sistema no se utiliza como criterio principal de riego, pero sí mejora la interpretación del entorno y puede ser útil para futuras reglas más completas.

La presión atmosférica se obtiene como dato adicional del sensor ambiental. Su influencia directa sobre la decisión de riego es menor que la de la humedad del suelo, la temperatura o la humedad relativa. Sin embargo, al estar disponible en el mismo sensor, no añade complejidad hardware significativa. En este trabajo se conserva como dato de contexto y como parte del histórico ambiental registrado.

Para medir temperatura, humedad relativa y presión se ha seleccionado el BME280. Este componente integra en un único sensor digital la medida de temperatura, humedad y presión, lo que reduce el número de módulos necesarios y simplifica el cableado. Bosch Sensortec lo describe como un sensor combinado de humedad, presión y temperatura, orientado a aplicaciones de bajo consumo y tamaño reducido \cite{bosch_bme280_datasheet}. En el prototipo se utiliza mediante bus I2C, lo que permite compartir las líneas de comunicación con otros sensores digitales.

La luminosidad se incorpora como indicador de exposición solar. Aunque no determina directamente el contenido de agua del suelo, ayuda a contextualizar las condiciones ambientales. Una zona con mayor exposición solar puede presentar mayor evaporación y calentamiento, mientras que una zona sombreada puede conservar humedad durante más tiempo. Esta variable resulta útil para interpretar diferencias entre estaciones o entre distintos momentos del día.

Para esta medida se ha seleccionado el BH1750, integrado habitualmente en módulos GY-302. Se trata de un sensor digital de luminosidad con interfaz I2C. Su elección se debe a que entrega directamente medidas en lux, evitando estimar la luminosidad a partir de una lectura analógica sin escala física clara. La documentación del BH1750FVI lo describe como un sensor digital de luz ambiente con interfaz I2C y conversión directa de iluminancia \cite{rohm_bh1750_datasheet}.

Además, el uso de I2C para el BME280 y el BH1750 simplifica la integración, ya que ambos sensores pueden compartir las líneas SDA y SCL del Arduino UNO siempre que sus direcciones no coincidan.

El detalle de los componentes empleados se recoge en el Anexo~\ref{anexo:materiales}; el conexionado eléctrico, en el Anexo~\ref{anexo:esquemas_electricos}; y la estrategia de validación, en los Anexos~\ref{anexo:plan_pruebas} y \ref{anexo:trazabilidad_requisitos_pruebas}. De esta forma, el cuerpo principal mantiene la justificación técnica de la elección de variables y sensores, mientras que la información reproducible del montaje y de las pruebas queda documentada como material complementario.

En conjunto, la combinación seleccionada cubre las variables mínimas necesarias para una primera versión funcional de TierraViva: una variable principal de decisión, la humedad del suelo, y varias variables ambientales de contexto. En fases posteriores podrían añadirse sensores más avanzados, como caudal, nivel de depósito, conductividad eléctrica o pH, pero incorporarlos en esta primera versión aumentaría la complejidad sin ser imprescindible para validar la arquitectura general del sistema.

\section{Elección de plataforma de control local y supervisión}
\label{sec:eleccion_plataformas_control}

La arquitectura de TierraViva separa claramente dos niveles funcionales. Por un lado, las estaciones de campo necesitan una plataforma sencilla y cercana al hardware, capaz de leer sensores, comunicarse con el módulo LTE, aplicar reglas locales de riego y controlar el relé de la bomba. Por otro lado, el sistema necesita una plataforma con mayor capacidad software para consultar datos, almacenarlos, exponer una API y servir el dashboard web. Esta segunda plataforma no actúa como cerebro del riego, sino como sistema de supervisión e histórico. Esta diferencia de funciones justifica el uso combinado de Arduino UNO y Raspberry Pi 5, en lugar de concentrar todo el sistema en una única plataforma.

\begin{figure}[H]
    \centering
    \includegraphics[width=\textwidth]{figs/figura_3_7_plataformas_control_supervision.png}
    \caption{Separación de responsabilidades entre Arduino UNO y Raspberry Pi 5.}
    \label{fig:cap3_plataformas_control_supervision}
\end{figure}

Arduino UNO se ha seleccionado como plataforma principal de las estaciones de campo. Se trata de una placa basada en el microcontrolador ATmega328P, con funcionamiento a 5 V, 14 pines digitales, 6 entradas analógicas, 32 KB de memoria flash, 2 KB de SRAM y frecuencia de reloj de 16 MHz \cite{arduino_uno_rev3_specs}. Aunque sus prestaciones son limitadas frente a plataformas más modernas, resultan suficientes para las tareas previstas en la estación: lectura de sensores, gestión de tiempos, comunicación serie con el módulo A7670E-LASA y control de una salida digital asociada al relé.

Una ventaja importante de Arduino UNO en este proyecto es su sencillez de integración. La lectura del sensor capacitivo de humedad del suelo puede realizarse mediante una entrada analógica, mientras que los sensores BME280 y BH1750 pueden compartir el bus I2C del Arduino. Además, el control del relé requiere únicamente una salida digital. Esta correspondencia directa entre necesidades del sistema y recursos de la placa facilita el desarrollo y la depuración del prototipo.

También se ha tenido en cuenta la disponibilidad de documentación, librerías y ejemplos. En un TFG con integración de varios subsistemas, la plataforma de estación no debe convertirse en el principal foco de incertidumbre. Arduino UNO permite validar de forma rápida sensores, salidas digitales, comunicación serie y temporización. Esta característica ha resultado útil durante las pruebas iniciales, donde se pudo comprobar primero el funcionamiento básico de la placa, después el bus I2C y finalmente la lectura integrada de sensores.

No obstante, la elección de Arduino UNO implica aceptar limitaciones. La memoria disponible es reducida, no dispone de sistema operativo, no incorpora conectividad inalámbrica integrada y su capacidad de procesamiento es limitada. Tampoco es una plataforma adecuada para ejecutar una base de datos, un servidor web o procesos software complejos. Por ello, en TierraViva Arduino no se utiliza como controlador global del sistema, sino como controlador local de estación. Su papel es ejecutar tareas concretas, repetitivas y cercanas al hardware.

La Raspberry Pi 5 se ha seleccionado como sistema de supervisión del prototipo. A diferencia de Arduino UNO, Raspberry Pi 5 es un computador de placa reducida capaz de ejecutar un sistema operativo completo. La documentación oficial la describe con un procesador Arm Cortex-A76 de cuatro núcleos a 2,4 GHz, lo que la sitúa en un nivel de capacidad muy superior al de un microcontrolador clásico \cite{raspberry_pi5_product_brief}. En este proyecto, esa capacidad permite ejecutar varios componentes software: lectura de datos desde la plataforma cloud, almacenamiento en SQLite, API mediante FastAPI y dashboard web.

Esta elección permite separar las funciones críticas de adquisición y actuación local de las funciones de supervisión y análisis. La Raspberry Pi no necesita estar conectada físicamente a las estaciones ni leer directamente los sensores. Su función es actuar como sistema de supervisión: consulta la información disponible, mantiene un histórico, expone datos mediante una API y permite visualizar el estado del prototipo. Esta separación es importante en TierraViva porque las estaciones se plantean como nodos remotos desplegados en campo, mientras que la Raspberry puede ubicarse en otro lugar y comunicarse con ellas a través de la plataforma intermedia.

Centralizar todo en Arduino UNO no sería adecuado para el alcance completo del sistema. Aunque Arduino puede leer sensores y controlar un relé, no está pensado para mantener una base de datos, servir una interfaz web, ejecutar una API o gestionar históricos de forma cómoda. Forzar esas funciones en una plataforma tan limitada aumentaría la complejidad del firmware y reduciría la capacidad de depuración. Además, mezclar adquisición, comunicación, almacenamiento, visualización y lógica global en un único microcontrolador haría que el sistema fuera menos modular y más difícil de mantener.

Tampoco sería conveniente utilizar únicamente Raspberry Pi en las estaciones de campo. Aunque Raspberry Pi ofrece mucha más potencia, también introduce un consumo mayor, tiempos de arranque más largos y dependencia de un sistema operativo. Además, no dispone de entradas analógicas nativas, por lo que la lectura directa de sensores analógicos requeriría componentes adicionales. Para una estación remota alimentada en campo, que debe leer sensores, controlar un relé y mantener un estado seguro, un microcontrolador sencillo resulta más apropiado que un computador completo.

La combinación de ambas plataformas permite asignar a cada una el papel para el que resulta más adecuada. Arduino UNO se encarga de la interacción directa con el entorno físico: sensores, módulo de comunicaciones y relé. Raspberry Pi 5 aporta la capacidad necesaria para almacenar datos, servir una API y ofrecer una interfaz de supervisión. Esta separación reduce riesgos de integración y facilita validar cada bloque por separado.

Durante el diseño también se consideraron alternativas. ESP32, por ejemplo, incorpora WiFi y Bluetooth, ofrece mayor capacidad de procesamiento que Arduino UNO y trabaja de forma nativa a 3,3 V. Podría ser una opción interesante en sistemas IoT donde se quiera integrar conectividad inalámbrica directamente en el nodo. Sin embargo, también suelen aumentar la complejidad de configuración, depuración y desarrollo. Para el alcance de este TFG, la prioridad no era elegir la plataforma embebida más potente, sino una suficientemente fiable y sencilla para validar la arquitectura completa.

En conjunto, la elección de Arduino UNO y Raspberry Pi 5 responde a una decisión de diseño modular. Arduino permite construir estaciones de campo simples, reproducibles y cercanas al hardware. Raspberry Pi 5 aporta la capacidad necesaria para almacenar datos, servir una API y ofrecer una interfaz de supervisión. Esta combinación mantiene el equilibrio entre sencillez, coste, capacidad técnica y adecuación al alcance académico del proyecto.

\section{Selección de solución de comunicaciones para estaciones remotas}
\label{sec:seleccion_comunicaciones_remotas}

La comunicación entre las estaciones de campo y el resto del sistema es una de las decisiones más importantes de TierraViva. A diferencia de un montaje de laboratorio, donde los sensores pueden conectarse directamente a un ordenador o a una Raspberry Pi mediante USB o red local, el escenario planteado requiere estaciones remotas capaces de enviar datos y estado desde una zona de cultivo sin depender de una red WiFi local ni de una conexión física con la Raspberry Pi. Por tanto, la solución de comunicaciones debía ser compatible con un despliegue en campo, funcionar sin depender de una red WiFi local y permitir la integración con una plataforma de datos externa para supervisión remota.

Durante la fase inicial del proyecto se valoraron principalmente dos enfoques: una solución basada en LoRa/LoRaWAN y una solución basada en conectividad móvil LTE. Ambas alternativas eran técnicamente razonables, pero respondían a prioridades distintas. LoRa y LoRaWAN resultaban especialmente atractivas por su bajo consumo, largo alcance y orientación a redes de sensores distribuidas. LTE, en cambio, ofrecía una integración más directa con servicios en Internet, a cambio de un mayor consumo energético y de la dependencia de cobertura móvil.

La alternativa LoRa/LoRaWAN encajaba bien con la idea inicial del proyecto. LoRa es una modulación de largo alcance y bajo consumo diseñada para comunicaciones de baja tasa de datos, muy adecuada para sensores que envían medidas periódicas y no necesitan transmitir grandes volúmenes de información \cite{semtech2015lora_modulation,augustin2016lora}. En un sistema agrícola, esta característica resulta interesante porque las estaciones suelen transmitir pocos datos: humedad del suelo, temperatura, humedad relativa, luminosidad, presión atmosférica y estado del actuador. Además, el enfoque de bajo consumo es coherente con estaciones alimentadas mediante batería o energía solar.

LoRaWAN añadía una capa de red sobre LoRa, proporcionando una arquitectura más estructurada para gestionar dispositivos, gateways y servidores de red \cite{lora_alliance_104}. Desde el punto de vista académico, esta opción tenía mucho interés: permitía estudiar una tecnología ampliamente utilizada en IoT, analizar su arquitectura y plantear un despliegue de nodos de campo con comunicaciones de largo alcance. También era coherente con escenarios rurales donde no siempre hay conectividad WiFi y donde interesa cubrir distancias superiores a las habituales en redes domésticas.

Sin embargo, al trasladar esta alternativa al prototipo real aparecieron dificultades prácticas importantes. La primera era la necesidad de disponer de infraestructura adicional. En LoRa punto a punto bastaría con módulos compatibles en las estaciones y en el receptor, pero se perderían parte de las ventajas de una arquitectura LoRaWAN completa. En LoRaWAN, por el contrario, sería necesario contar con un gateway, configurar la red, gestionar la integración con un servidor LoRaWAN y conectar posteriormente esa información con el sistema de supervisión. Esta infraestructura aumentaba el alcance del proyecto y desplazaba una parte importante del esfuerzo hacia la propia red de comunicaciones.

También se detectó un riesgo de integración asociado a la selección de módulos. Para un despliegue en Europa es necesario trabajar en la banda adecuada, normalmente 868 MHz, y comprobar que los módulos, antenas, placas adaptadoras y niveles lógicos sean compatibles entre sí. En el caso de Arduino UNO, además, muchos módulos LoRa trabajan a 3,3 V, mientras que la placa funciona a 5 V, por lo que puede ser necesario añadir conversores de nivel y una alimentación de 3,3 V suficientemente estable. Estos detalles no invalidan la solución, pero introducen más puntos de fallo en una fase del proyecto donde el objetivo principal era validar una arquitectura completa de monitorización, almacenamiento, visualización y actuación.

Otro aspecto relevante fue la diferencia entre LoRa y LoRaWAN. Aunque a veces se mencionan juntos, no son equivalentes. LoRa define la capa física, mientras que LoRaWAN define una arquitectura de red con gateways, servidor de red y mecanismos de gestión de dispositivos \cite{adelantado2017limits}. Para el proyecto, esta distinción era importante porque una solución LoRa punto a punto habría sido más sencilla, pero menos representativa de una red IoT completa; y una solución LoRaWAN habría sido más completa, pero también más costosa en tiempo e infraestructura.

La alternativa basada en LTE se planteó como una forma de reducir ese riesgo de integración. En lugar de desplegar una infraestructura radio propia, cada estación utiliza un módulo A7670E-LASA con tarjeta SIM para conectarse directamente a la red móvil. La comunicación con el exterior se realiza mediante comandos AT y peticiones HTTP, lo que permite enviar datos a una plataforma cloud sin necesidad de gateway propio. Esta decisión simplifica la arquitectura de comunicaciones: la estación no necesita que exista una Raspberry Pi cercana ni una pasarela local en la parcela, sino únicamente cobertura móvil suficiente y una configuración correcta del APN.

La elección de LTE no elimina las restricciones técnicas. El módulo requiere una alimentación más exigente que una solución LoRa, especialmente por los picos de corriente durante el registro en red o la transmisión de datos. Además, el sistema pasa a depender de la cobertura del operador móvil, de la disponibilidad de una tarjeta SIM y del acceso a Internet. Estas limitaciones son relevantes y deben tenerse en cuenta en el diseño energético y en el modo seguro de funcionamiento. Si la estación no puede comunicar, el sistema no debe quedar en un estado peligroso ni mantener el riego activo de forma indefinida.

Aun así, para el alcance concreto del TFG, LTE ofrecía una ventaja decisiva: permitía validar antes el ciclo completo de publicación y supervisión. Las estaciones podían leer sensores, enviar telemetría mediante HTTP, integrarse con ThingSpeak y dejar sus datos disponibles para que la Raspberry Pi los consultara posteriormente. Esto encaja con la arquitectura final de TierraViva, en la que la Raspberry Pi no está conectada físicamente a las estaciones ni decide el riego, sino que actúa como sistema de supervisión e histórico. La comunicación entre estaciones y sistema de supervisión, por tanto, no se resuelve mediante USB, puerto serie o red local, sino mediante la publicación y consulta de datos a través de Internet y de la plataforma intermedia.

La decisión final fue utilizar LTE con el módulo A7670E-LASA. Esta elección no implica que LoRa/LoRaWAN sea una alternativa peor desde el punto de vista tecnológico. De hecho, para una versión futura orientada a bajo consumo y despliegue en parcelas sin cobertura móvil, LoRa o LoRaWAN podrían ser opciones muy adecuadas. La decisión se basa en el contexto del proyecto: se buscaba una solución funcional, verificable y defendible dentro del tiempo disponible, priorizando la integración completa del sistema frente al desarrollo de una infraestructura de comunicaciones propia.

La validación preliminar del módulo LTE reforzó esta decisión. Antes de integrarlo con Arduino, el A7670E-LASA se probó mediante comandos AT desde un ordenador. Las pruebas permitieron comprobar que el módulo respondía correctamente, reconocía la SIM, obtenía señal, se registraba en red LTE, disponía de dirección IP y podía realizar peticiones HTTP. Estos resultados no sustituyen a las pruebas de integración completas, que se desarrollan más adelante, pero sí permitieron confirmar que la vía LTE era viable para el prototipo.

En términos de diseño, la consecuencia principal de esta elección es que ThingSpeak se convierte en una capa intermedia de comunicación. Las estaciones publican su telemetría y estado mediante HTTP, y la Raspberry Pi consulta esos datos desde la nube para almacenarlos, visualizarlos y supervisar el funcionamiento del prototipo. La decisión de riego no depende de un flujo descendente de órdenes, sino de reglas locales ejecutadas en cada estación. Este enfoque reduce la dependencia de la conectividad externa para la actuación física y reserva la comunicación remota para telemetría, estado, histórico y supervisión.

Por tanto, la solución LTE adoptada responde a un criterio de ingeniería pragmático. LoRa/LoRaWAN se estudió por su adecuación a IoT agrícola, bajo consumo y largo alcance, pero se descartó como solución principal por el riesgo de aumentar demasiado la complejidad de comunicaciones. LTE con A7670E-LASA permite centrar el esfuerzo en el objetivo global de TierraViva: construir un prototipo capaz de medir, comunicar, almacenar, visualizar y actuar de forma segura mediante decisión local en las estaciones.

\section{Elección de plataforma cloud: ThingSpeak}
\label{sec:eleccion_plataforma_cloud}

La elección de la plataforma cloud se ha realizado teniendo en cuenta el papel que debía desempeñar dentro de TierraViva. En este proyecto, la nube no se utiliza como un elemento añadido únicamente para representar gráficas, sino como una capa intermedia entre las estaciones de campo y el sistema de supervisión. Las estaciones deben poder enviar telemetría desde una ubicación remota mediante LTE y la Raspberry Pi debe poder consultar esos datos sin estar conectada físicamente a ellas. En la arquitectura final, esta capa no se utiliza para enviar órdenes de riego, sino para publicar telemetría, estado de relé y códigos de funcionamiento generados por las propias estaciones.

En el capítulo anterior se describieron varias alternativas de plataformas cloud para IoT, como Ubidots, Adafruit IO, Blynk, ThingsBoard o soluciones basadas en un broker MQTT propio. Todas ellas podrían ser válidas en determinados escenarios, pero no ofrecen el mismo equilibrio entre sencillez, control, coste, curva de aprendizaje y facilidad de integración con un prototipo académico. En este TFG no se buscaba desplegar una infraestructura cloud compleja, sino disponer de una plataforma suficientemente fiable y accesible para validar el ciclo completo de monitorización y control.

Una alternativa posible habría sido utilizar un broker MQTT accesible desde Internet. Esta opción resulta atractiva desde el punto de vista técnico, ya que MQTT está diseñado para comunicaciones IoT y permite un modelo de publicación/suscripción más adecuado para sistemas con múltiples nodos. Sin embargo, en el caso concreto de TierraViva habría implicado añadir un servidor o servicio externo, configurar autenticación, gestionar reconexiones y adaptar la comunicación del módulo LTE a ese esquema. Para un prototipo cuyo objetivo principal es validar una arquitectura completa, esta complejidad adicional no aportaba una mejora proporcional.

También se consideraron plataformas más completas, como ThingsBoard, que ofrecen más posibilidades de gestión de dispositivos, reglas, visualización y escalabilidad. No obstante, precisamente por ser más completas, requieren una configuración inicial mayor. En una solución industrial o en un despliegue con muchos dispositivos, esta inversión puede estar justificada. En TierraViva, donde el número de estaciones es reducido y la prioridad es demostrar el funcionamiento extremo a extremo, una plataforma más ligera resulta más adecuada.

ThingSpeak se ha seleccionado porque proporciona una estructura sencilla basada en canales y campos, una API HTTP fácil de utilizar desde dispositivos embebidos y herramientas básicas de visualización. Según la documentación de MathWorks, ThingSpeak permite escribir datos en canales mediante llamadas HTTP de la API REST, además de otros métodos como MQTT o funciones de MATLAB \cite{thingspeak_docs,thingspeak_write_data}. Esta característica encaja especialmente bien con el módulo A7670E-LASA, ya que el envío de datos puede implementarse mediante comandos AT y peticiones HTTP, sin necesidad de incorporar una pila de comunicación más compleja en el firmware de Arduino.

La separación por canales de estación evita mezclar los datos de distintas zonas monitorizadas y permite que la Raspberry Pi consulte de forma independiente la telemetría y el estado de cada nodo. Esta decisión mejora la trazabilidad del sistema y facilita la depuración, ya que se puede comprobar por separado si cada estación está enviando medidas correctamente, si publica su estado operativo y si se han registrado eventos de riego o incidencias.

En la estructura actual se utilizan canales diferenciados para cada estación: TierraViva\_A y TierraViva\_B. Durante el diseño se valoró utilizar ThingSpeak también como mecanismo de control descendente, pero esa opción se descartó al desplazar la decisión de riego al firmware de cada estación. De este modo, la plataforma queda reservada para telemetría y estado, y se evita que una entrada antigua en la nube pueda condicionar una actuación física.

Otra razón importante para elegir ThingSpeak es la facilidad de lectura desde la Raspberry Pi. La Raspberry Pi puede consultar los últimos datos publicados mediante peticiones HTTP y recibir la información en formato estructurado. La documentación de MathWorks permite leer datos de un canal mediante la API y obtener respuestas en formatos como JSON o CSV \cite{thingspeak_read_data}. Esto encaja con la arquitectura software planteada para la Raspberry, donde los datos recibidos se almacenan posteriormente en SQLite y se presentan mediante una API y un dashboard propios.

ThingSpeak también permite mantener una primera visualización de los datos directamente en la plataforma. Aunque el dashboard final de TierraViva se desarrolla en la Raspberry Pi, las gráficas de ThingSpeak resultan útiles durante la fase de pruebas, porque permiten comprobar rápidamente si los datos están llegando a la nube antes de integrarlos en el resto del sistema. Durante las pruebas, disponer de esa doble visualización ayuda a acotar el fallo: si una lectura aparece en ThingSpeak pero no en el dashboard local, el problema estará probablemente en la lectura desde la Raspberry o en el almacenamiento; si no aparece en ThingSpeak, el fallo estará antes, en la estación, en el módulo LTE o en la petición HTTP.

La plataforma también presenta limitaciones que deben asumirse. ThingSpeak no se comporta como un sistema de tiempo real estricto. El envío y la consulta de datos se basan en peticiones y en intervalos de actualización, por lo que existe una latencia asociada. En la arquitectura final de TierraViva esta limitación no compromete la actuación sobre el riego, ya que la decisión crítica se ejecuta localmente en la estación y no depende de recibir una instrucción externa de riego.

En el caso de TierraViva, la latencia de ThingSpeak es aceptable porque su papel principal es registrar telemetría, estado y eventos para supervisión posterior. El riego no requiere que la Raspberry responda en milisegundos, sino que la estación aplique reglas verificables, limite el tiempo de bomba activa y publique información suficiente para reconstruir lo ocurrido. Por ello, resulta más importante diseñar correctamente el firmware local y los códigos de estado que reducir al mínimo la latencia de consulta desde la Raspberry Pi.

La elección de ThingSpeak, por tanto, responde a un criterio de equilibrio. No es la plataforma más completa ni la más flexible para un despliegue industrial, pero sí es adecuada para un prototipo académico donde se necesita integrar sensores, LTE, almacenamiento remoto, consulta desde Raspberry Pi y supervisión de estados publicados por estaciones autónomas. Su principal ventaja es que permite validar la arquitectura completa sin desplazar el esfuerzo hacia el mantenimiento de una infraestructura cloud propia.

En conjunto, ThingSpeak actúa como punto de desacoplo entre las estaciones y la Raspberry Pi. Las estaciones no necesitan conocer la ubicación de la Raspberry ni mantener una conexión directa con ella; publican telemetría, estado del relé, eventos de sistema y códigos auxiliares de diagnóstico en la nube. La Raspberry, por su parte, consulta esa información para construir el histórico, alimentar la API y servir el dashboard, sin intervenir en la decisión local de riego. Esta separación es coherente con el objetivo de TierraViva: construir un sistema modular, verificable y preparado para funcionar con estaciones remotas autónomas.

La estructura concreta de canales utilizada en TierraViva se desarrolla con mayor detalle en el Capítulo~\ref{cap:capitulo4}, donde se documentan los canales TierraViva\_A y TierraViva\_B, así como la codificación de los campos empleados para telemetría, estado y eventos.

\label{sec:eleccion_arquitectura_software_raspberry}

La Raspberry Pi se ha seleccionado como sistema de supervisión software de TierraViva. Su función no es sustituir a las estaciones de campo, leer directamente los sensores ni decidir la activación de la bomba, sino consultar la información publicada por las estaciones, registrar un histórico local y ofrecer una interfaz de consulta. Esta separación resulta importante porque las estaciones se encuentran en campo y se comunican de forma remota, mientras que la Raspberry actúa como nodo de supervisión e histórico.

La arquitectura software de supervisión se apoya en tres bloques principales: almacenamiento local, API y dashboard. SQLite se selecciona como base de datos local por su sencillez de despliegue y por ser suficiente para conservar el histórico de lecturas, estados e incidencias del prototipo sin instalar un servidor de base de datos adicional \cite{sqlite_about}. Esta decisión permite que la Raspberry Pi mantenga una memoria propia del sistema, complementaria a los datos publicados en ThingSpeak.

FastAPI se selecciona como framework para construir la API de supervisión en Python \cite{fastapi_docs}. Su papel dentro de TierraViva es actuar como capa intermedia entre la base de datos y la interfaz web, evitando que el dashboard acceda directamente a SQLite o a los detalles internos de almacenamiento. La API permite consultar datos mediante peticiones HTTP y deja preparada la arquitectura para que otros clientes puedan reutilizar la misma información en futuras ampliaciones.

El dashboard web constituye la capa de presentación del sistema. Su objetivo es mostrar de forma comprensible las últimas lecturas, el estado de las estaciones y la información operativa publicada por cada nodo. De esta manera, la Raspberry Pi no se limita a almacenar datos, sino que los transforma en información útil para supervisar el comportamiento del prototipo.

La lógica de decisión de riego no se mantiene en la Raspberry Pi en la arquitectura final. Aunque este dispositivo tiene capacidad suficiente para comparar estaciones o aplicar reglas más complejas, se ha decidido desplazar la decisión crítica al nodo de campo. Esta elección reduce la dependencia de la red, elimina la necesidad de enviar comandos remotos y permite que cada estación mantenga un comportamiento seguro aunque la Raspberry no esté disponible.

La Raspberry conserva un papel relevante dentro del sistema, pero orientado a supervisión. Puede detectar si una estación deja de publicar datos, mostrar el último estado conocido del relé, conservar históricos y facilitar el análisis posterior de las pruebas. De esta forma, el sistema mantiene trazabilidad sin convertir la supervisión en un requisito para que el riego pueda ejecutarse.

Una ventaja adicional de mantener un histórico local es la posibilidad de analizar el comportamiento del sistema más allá de la última lectura recibida. El histórico permite revisar tendencias, detectar periodos sin comunicación, comparar estaciones y documentar pruebas. También deja preparada la arquitectura para futuras mejoras, como reglas más avanzadas, detección de anomalías o modelos predictivos basados en datos acumulados. En esta versión del TFG, estas posibilidades no se presentan como inteligencia artificial implementada de forma completa, sino como una evolución razonable cuando exista un volumen suficiente de datos fiables.

Con esta organización, la Raspberry Pi mantiene un papel claro dentro del sistema: no controla físicamente el riego, pero convierte los datos publicados por las estaciones en información consultable y persistente. SQLite permite conservar un histórico local, FastAPI proporciona una interfaz de consulta mediante HTTP y el dashboard facilita la supervisión del prototipo. La Raspberry queda así definida como sistema de supervisión: consulta, registra y expone información, mientras que la decisión y la ejecución segura de la actuación permanecen en la estación de campo.

\section{Riesgos técnicos y medidas de mitigación}
\label{sec:riesgos_tecnicos_mitigacion}

El diseño de TierraViva debe contemplar fallos de sensores, alimentación, comunicación, software y actuación. Esta consideración es especialmente importante porque el prototipo no se limita a monitorizar variables ambientales, sino que acciona físicamente una bomba de agua. Por ello, el criterio general adoptado es conservador: ante una lectura inválida, una condición no verificable o un fallo relevante, la estación debe mantener la bomba apagada.

La Tabla~\ref{cuadro:riesgos_mitigacion} resume los riesgos técnicos principales considerados durante el diseño. El análisis completo de probabilidad, impacto, criticidad, riesgo residual y pruebas asociadas se desarrolla en el Anexo~\ref{anexo:gestion_riesgos}.

Estas medidas siguen un principio común: separar supervisión y control local. La Raspberry Pi permite registrar, consultar y visualizar el estado del sistema, pero la seguridad de la actuación reside en la estación de campo. De este modo, una caída del dashboard, una pérdida de comunicación o un dato no fiable no deben provocar una activación no controlada de la bomba.
