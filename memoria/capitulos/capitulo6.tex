Una vez descrita la implementación hardware y \textit{firmware} de las estaciones de campo, este capítulo se centra en la parte software que permite supervisar el sistema desde la Raspberry Pi y conservar un histórico de funcionamiento.  El papel de la Raspberry Pi consiste en consultar la información publicada por las estaciones en ThingSpeak, normalizar las lecturas recibidas, almacenarlas en una base de datos local y exponerlas mediante una API y un \textit{dashboard} web. Esta separación permite mantener el comportamiento autónomo de las estaciones incluso si la Raspberry Pi está apagada, sin conexión o en mantenimiento.

El software desarrollado no apareció directamente en su forma final. Antes de cerrar la arquitectura remota basada en LTE y ThingSpeak, se implementó un prototipo local con MQTT para validar la cadena básica de adquisición, transporte, almacenamiento y visualización de datos. Dicho prototipo no forma parte de la arquitectura definitiva, pero resulta relevante porque permitió detectar necesidades reales del sistema, comprobar la utilidad de una arquitectura desacoplada y reducir el riesgo antes de trabajar con comunicaciones móviles y con ThingSpeak como plataforma intermedia.

El código asociado al proyecto se conserva en el repositorio público TierraViva\footnote{\url{https://github.com/ltejedorcruz/TierraViva/tree/main}}, incluyendo tanto la versión final en desarrollo como los prototipos intermedios utilizados durante la evolución del TFG.

\section{Prototipo local previo con MQTT}
\label{sec:prototipo_local_mqtt}

Antes de cerrar la arquitectura final basada en estaciones remotas con LTE y ThingSpeak, se desarrolló un prototipo local sobre Raspberry Pi utilizando MQTT como mecanismo de comunicación interna. Esta fase se planteó como una validación controlada de la cadena software básica del sistema: adquisición de telemetría, transporte de mensajes, almacenamiento local, API y visualización web, antes de abordar el despliegue en campo.

El prototipo se conserva en el directorio \texttt{prototipos/prototipo\_local\_mqtt/} del repositorio \cite{tierraviva_github_mqtt}. Su valor dentro del TFG reside en haber servido como fase previa de aprendizaje e integración. Permitió comprobar que una arquitectura desacoplada por capas facilitaba la depuración: recepción de datos, persistencia, API y \textit{dashboard} podían probarse de forma progresiva antes de incorporar la complejidad de la comunicación móvil.

El enfoque MQTT se descartó como arquitectura final porque dependía de un flujo más local y ofrecía peor encaje con la publicación remota desde estaciones desplegadas fuera del entorno de laboratorio. La solución definitiva sustituye esa comunicación local por publicación LTE/HTTP en ThingSpeak, manteniendo la decisión de riego en el \textit{firmware} de cada estación y dejando la Raspberry Pi como nodo de supervisión, ingesta, almacenamiento, API y \textit{dashboard}.

La evolución desde el prototipo MQTT hasta la arquitectura final se recoge como decisión técnica en el Anexo~\ref{anexo:seguimiento_decisiones}. El flujo definitivo de funcionamiento se resume en el Anexo~\ref{anexo:diagramas_flujo_funcionamiento}, mientras que la estructura de telemetría empleada en ThingSpeak se documenta en el Anexo~\ref{anexo:estructura_thingspeak_estados}.

Una vez descartado el prototipo local como arquitectura final, la Raspberry Pi se adapta al modelo definitivo de TierraViva: las estaciones publican su telemetría y estado en ThingSpeak mediante LTE/HTTP, y la Raspberry consulta posteriormente esa información. El primer bloque software de la Raspberry consiste, por tanto, en consultar periódicamente la plataforma, recuperar la última publicación disponible de cada estación y convertirla a una estructura interna común.

Este bloque se implementa en el módulo principal de ingesta, asociado al fichero \texttt{main.py}, disponible en el repositorio público del proyecto \cite{tierraviva_github}. Su responsabilidad consiste en mantener actualizada la copia local de los datos publicados en la nube. De esta forma, la Raspberry Pi lee, normaliza, registra y sirve información al \textit{dashboard}, dentro de su papel como sistema de supervisión.

La ingesta utiliza el identificador \texttt{entry\_id} de ThingSpeak para diferenciar una lectura nueva de una lectura ya procesada. Esta comprobación evita duplicados cuando la Raspberry consulta la plataforma con más frecuencia que la publicación real de las estaciones. Cuando una entrada es nueva, el sistema almacena la información normalizada junto con el identificador de estación, el \texttt{entry\_id}, la marca temporal de ingesta y la respuesta original recibida.

El tratamiento de errores se plantea de forma conservadora. Si falla la consulta HTTP, si ThingSpeak devuelve una respuesta no válida o si no se recibe un \texttt{entry\_id} interpretable, el módulo registra la incidencia y continúa con el siguiente ciclo. No se fuerza una inserción incompleta ni se detiene el sistema completo por un fallo puntual de lectura. Esta decisión es coherente con la arquitectura final: una pérdida temporal de supervisión desde Raspberry Pi no debe afectar al comportamiento local de las estaciones.

En resumen, la lectura de ThingSpeak transforma la plataforma \textit{cloud} en una fuente de datos estructurada para el sistema local de supervisión. La Raspberry recupera la información publicada por cada nodo, filtra duplicados, trata errores de lectura y prepara los datos para su almacenamiento y posterior visualización.

\section{Base de datos SQLite}
\label{sec:base_datos_sqlite}

\begin{wrapfigure}{r}{0.32\textwidth}
    \vspace{-12pt}
    \centering
    \includegraphics[width=0.30\textwidth]{figs/sqlite_logo.jpeg}
    \caption{Logotipo de SQLite. Fuente: sitio oficial de SQLite \cite{sqlite_about}.}
    \label{fig:logo_sqlite}
    \vspace{-8pt}
\end{wrapfigure}

El bloque de almacenamiento local de TierraViva se implementa mediante SQLite. Su función es conservar en la Raspberry Pi una copia estructurada de la información recibida desde ThingSpeak, de forma que el \textit{dashboard} y la API no dependan únicamente de consultar la plataforma \textit{cloud} en tiempo real. Esta base de datos permite mantener un histórico de lecturas, registrar eventos de riego o actuación, conservar estados internos del sistema y facilitar tareas de depuración durante las pruebas.

SQLite resulta adecuado para este prototipo porque funciona como una base de datos embebida, almacenada en un fichero local, sin necesidad de desplegar un servidor de base de datos adicional. En una Raspberry Pi esto simplifica la instalación y reduce el número de servicios que deben mantenerse activos. Para el alcance del TFG, donde el volumen de datos es moderado y la prioridad es validar el funcionamiento completo del sistema, esta solución ofrece un equilibrio razonable entre simplicidad, persistencia y capacidad de consulta \cite{sqlite_about}.

La implementación se concentra en el módulo \texttt{database.py}, disponible en el repositorio del proyecto \cite{tierraviva_github}. Este módulo define la ubicación de la base de datos, crea los directorios necesarios, abre las conexiones SQLite mediante la biblioteca \texttt{sqlite3} de Python \cite{python_sqlite3_docs} y proporciona funciones auxiliares de inserción, consulta y actualización de estado. La base se almacena bajo el directorio de trabajo de TierraViva, concretamente en el fichero \texttt{tierraviva.db}, dentro de la carpeta de datos configurada para la Raspberry Pi.

El acceso a la base de datos se encapsula mediante una función de conexión. Esta función no solo abre el fichero SQLite, sino que también configura la conexión para devolver filas accesibles por nombre de columna y activa opciones como \texttt{journal\_mode=WAL} y \texttt{foreign\_keys}. El modo WAL, \textit{Write-Ahead Logging}, mejora el comportamiento cuando existen lecturas y escrituras próximas en el tiempo, algo habitual en TierraViva porque el proceso de ingesta escribe datos mientras la API puede estar consultándolos para el \textit{dashboard}.

El modelo local se organiza en tres tablas principales: \texttt{readings}, \texttt{valve\_events} y \texttt{system\_state}. Esta división separa los datos de telemetría, los eventos asociados a la actuación y el estado interno del sistema de supervisión. De esta forma se evita mezclar en una única tabla información de naturaleza distinta.

La Figura~\ref{fig:er_tierraviva_sqlite} resume el modelo entidad--relación simplificado de la base de datos local. El objetivo del diagrama es mostrar con claridad cómo se separan las lecturas de telemetría, los eventos asociados a la actuación y el estado interno utilizado por la Raspberry Pi durante la supervisión.

El módulo \texttt{database.py}, disponible en el repositorio del proyecto \cite{tierraviva_github}, incorpora además comprobaciones de esquema para facilitar la evolución incremental de la base de datos durante el desarrollo. El uso de SQLite resulta adecuado para este prototipo porque evita desplegar un servidor adicional y mantiene la persistencia en un fichero local de la Raspberry Pi \cite{sqlite_about}.

\section{Interpretación de estados publicados por las estaciones}
\label{sec:interpretacion_estados_estaciones}

La Raspberry Pi interpreta los datos que la estación ya ha publicado en ThingSpeak, los almacena de forma coherente y ofrece una representación comprensible al \textit{dashboard}. Esta separación organiza el sistema en dos planos diferenciados: el \textit{firmware} de estación genera los estados operativos y la Raspberry los transforma en información consultable para supervisión, como se ha descrito en el Capítulo~\ref{cap:implementacion_hardware_firmware}.

Además de las variables ambientales, cada publicación incluye tres campos de estado: \texttt{relay\_state}, \texttt{system\_event} y \texttt{debug\_code}. Estos campos permiten conocer si la bomba estaba activada, qué evento principal se había producido y qué información auxiliar de diagnóstico acompañaba a la lectura. La Raspberry normaliza estos valores, los almacena en SQLite y los sirve mediante la API para que el \textit{dashboard} pueda mostrar estados comprensibles.

\section{API FastAPI}
\label{sec:api_fastapi}

La API local de TierraViva se implementa con FastAPI y actúa como capa de servicio entre la base de datos SQLite y el \textit{dashboard} web. Su función principal es exponer los datos almacenados en la Raspberry Pi mediante peticiones HTTP, evitando que la interfaz acceda directamente a la base de datos o tenga que conocer los detalles internos del almacenamiento.

Trabaja sobre la información ya ingerida desde ThingSpeak y almacenada en SQLite, proporcionando una capa de consulta estructurada para el \textit{dashboard} web y para posibles clientes futuros. Esta separación mantiene una organización clara entre almacenamiento, lógica de consulta y presentación de datos.

La API cumple cuatro responsabilidades principales:

\begin{itemize}
    \item consultar las funciones de acceso a datos definidas en \texttt{database.py};
    \item validar parámetros básicos de entrada, como estación o límites de consulta;
    \item enriquecer algunas respuestas con información útil para la interfaz;
    \item devolver los datos en formato JSON para que puedan ser consumidos por el \textit{dashboard}.
\end{itemize}

El módulo \texttt{database.py} conserva la lógica de persistencia y consulta sobre SQLite. Por su parte, \texttt{api.py} se limita a actuar como capa de exposición HTTP. Esta división evita mezclar almacenamiento, lógica de consulta e interfaz, y facilita que el \textit{dashboard} pueda evolucionar sin modificar la estructura interna de la base de datos.

La API expone un conjunto reducido de \textit{endpoints} orientados a supervisión: configuración activa, última lectura, histórico reciente, estadísticas y estado básico del servicio. Uno de los aspectos más relevantes de la API es la incorporación de información calculada que simplifica el trabajo del \textit{dashboard}. Por ejemplo, a partir de la última lectura puede calcularse la antigüedad del dato, una etiqueta de frescura y una clasificación básica de humedad del suelo. De este modo, la interfaz no necesita repetir lógica de interpretación en JavaScript.

La API también ayuda a separar responsabilidades en la visualización. El \textit{dashboard} solicita datos ya estructurados, mientras que la API concentra las reglas de consulta y preparación de respuesta. Así se reduce el acoplamiento entre \textit{frontend} y base de datos, y facilita la depuración: si una lectura aparece incorrecta en la interfaz, puede comprobarse primero la respuesta JSON de la API antes de revisar la capa visual.

En resumen, FastAPI permite convertir la información almacenada localmente en una interfaz de consulta clara y reutilizable. En TierraViva, sirve datos al \textit{dashboard}, facilita la consulta del histórico y permite comprobar el estado básico del sistema software.

\section{\textit{Dashboard} web de supervisión}
\label{sec:dashboard_web_supervision}

El \textit{dashboard} web es la página de supervisión de TierraViva. Está alojado en la Raspberry Pi y se sirve desde la propia aplicación FastAPI ejecutada mediante Uvicorn, de forma que puede consultarse desde un navegador conectado al sistema. Su función es transformar los datos almacenados y expuestos por la API en una vista visual del estado del prototipo.

En la implementación actual, el fichero fuente de la interfaz se encuentra en:

\begin{center}
\texttt{dashboard/index.html}
\end{center}

Durante el despliegue, el \textit{script} \texttt{tierraviva.sh} copia los recursos del directorio \texttt{dashboard/} al directorio \texttt{frontend/}. Desde ahí, FastAPI sirve la página principal en la ruta \texttt{/} y los recursos gráficos en la ruta \texttt{/images}. De este modo, la Raspberry Pi actúa también como servidor web del panel de supervisión.

El fichero \texttt{index.html} contiene la estructura HTML de la interfaz, los estilos CSS embebidos en una sección \texttt{<style>} y la lógica JavaScript embebida en una sección \texttt{<script>}. Esta organización mantiene una separación lógica entre estructura, estilo y comportamiento, al mismo tiempo que facilita el despliegue del prototipo y reduce el número de ficheros que deben sincronizarse durante las pruebas.

Desde el navegador, el \textit{dashboard} consulta periódicamente los \textit{endpoints} locales de la API para obtener la configuración activa, la última lectura, el histórico reciente, las estadísticas agregadas y el estado básico del servicio. La estación activa se selecciona desde la propia interfaz, permitiendo reutilizar la misma página para consultar estaciones distintas. La actualización se realiza interpretando siempre la frescura del dato para distinguir lecturas recientes de lecturas antiguas u obsoletas.

\section{Ejecución y gestión del sistema software}
\label{sec:ejecucion_gestion_software}

Para facilitar la puesta en marcha del software en la Raspberry Pi, el proyecto incluye el \textit{script} \texttt{tierraviva.sh}. Este \textit{script} agrupa las operaciones principales de despliegue y ejecución, evitando tener que lanzar manualmente cada componente desde la terminal.

El \textit{script} permite instalar dependencias, preparar el entorno virtual, preparar el directorio \texttt{frontend/} servido por FastAPI, arrancar el proceso de ingesta \texttt{main.py}, iniciar el servidor \texttt{api.py} mediante Uvicorn, consultar el estado de ejecución, detener los procesos y revisar los \textit{logs}. Esta automatización resulta útil durante las pruebas porque reduce errores repetitivos de arranque y deja una forma reproducible de iniciar el sistema.

Además de arrancar los procesos, el \textit{script} carga el fichero \texttt{.env} cuando está disponible. Esto permite mantener fuera del código fuente las claves de ThingSpeak y los identificadores de canal. Durante el arranque, el \textit{script} comprueba que existen las variables necesarias para consultar las estaciones configuradas, como los identificadores de canal y las claves de lectura de ThingSpeak. Si faltan identificadores de canal o claves de lectura, el proceso de ingesta registra el error en los \textit{logs} y evita arrancar con una configuración incompleta.

Esta capa de gestión conserva la arquitectura del sistema y aporta reproducibilidad al \textit{backend}. Su valor está en facilitar la ejecución, reducir errores de arranque y simplificar la depuración durante las pruebas.
